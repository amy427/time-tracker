# 备份、恢复与长期维护

## 自动备份的实际行为

`setup` 安装每天一次的 `maintenance` 触发器。每次先恢复未完成写入，再确保当前年份文件存在，然后选一个已经结束且缺失/变脏的月份或年份生成快照。优先较新的周期；一天最多一个周期，避免触发器超时。新月正常生成上个月备份，新年同时补上一年的年度备份。已结束的历史月份如果因离线补传、编辑、拆分或删除变化，会被标为 dirty，任务自动再生成新版本。

原始记录按开始时区的月份/年份筛选，并保留完整起止时间：跨年事件在开始年份备份中。恢复多年历史时，每个开始年份的年度备份都要导入。不要只恢复 2027 的备份然后期待它包含 2026 开始的跨年活动。

每次有三个内容文件与一个 manifest，文件名含周期、生成时间和随机后缀，旧快照不覆盖。Master/backup_index 标明每个周期最近成功的 manifest_file_id、生成时间、记录数及 dirty 标记。manifest 只有在所有文件生成后才写入；不完整生成留下的文件不会成为有效备份。

- `…-events.jsonl`：无损主数据，一行一个事件，秒数、时区与稳定 event_key 均保留。
- `…-events.csv`：二维表，可用 Excel/Python/数据库分析；危险公式前缀已转义。
- `…-metadata.json`：配置、当前活动、版本、日汇总、年汇总和文件索引快照。
- `…-manifest.json`：记录数、时间、版本、每个文件的 SHA-256 和字节数。

自动备份存放在同一个 Google 账号，不抵御整个账号丢失。每年至少把有效年度快照和 manifest 下载到电脑或另一种介质。超长期依赖定期迁移与介质更新，不能只依赖云服务承诺。

## 手动立即生成备份

1. Apps Script Editor 顶部选择 `backupYear`，Run，默认备份当前年。
2. 若指定年份，在编辑器临时新增包装函数：

```javascript
function backup2026() { backupYear(2026); }
```

3. 保存，选择 backup2026，Run。日志返回 manifest。
4. 指定月份可用 `function backupOctober(){ var lock=LockService.getScriptLock(); lock.waitLock(20000); try { backupPeriod_('2026-10'); } finally { lock.releaseLock(); } }`。备份函数不应由公开 URL 暴露。

## 检查备份健康

1. Apps Script 左侧 Executions 查看 maintenance 最近是否成功。触发器失败邮件来自 Google，项目本身不发送邮件。
2. Project Settings / Script Properties 的 `LAST_MAINTENANCE_OK`、`LAST_BACKUP_OK`、`LAST_MAINTENANCE_ERROR` 显示最近结果。
3. Master / backup_index 检查已经结束的月份都有有效 manifest，并且 dirty=false。初次建库或导入多年的历史可能需要多天补完；可逐年手动 backupYear 先生成年度保护副本。
4. 下载同一版本的 manifest、CSV、JSONL、metadata 到同一个文件夹。
5. 电脑离线执行：

```powershell
node scripts/check-backup.cjs "C:\你的备份目录\对应版本-manifest.json"
```

6. 看到校验通过。缺文件、文件损坏、秒数不符或重复 UUID 都会拒绝。

## 云端完整恢复

1. 保留原 Drive 文件夹，不删除它。按部署教程建立新的 Apps Script 项目与空数据库，可重用原身份 Client ID 和前端 origin。
2. PWA 设置改为新后端 /exec 网址，Google 登录。确认当前活动为空，待同步为 0。
3. 在设置展开“校验与恢复开放格式备份”。选择同一版本的 manifest、events.jsonl、metadata.json（也可同时选 CSV 校验）。
4. 点击校验备份，核对周期、记录数和生成时间。
5. 点击导入已校验记录，确认。工具每批 5 条，服务器原子恢复计划更新 Raw、daily_summary 和 annual_summary。
6. 网络超时会保留未确认的原批次 UUID。联网后同步完成，再重新导入该文件也可安全去重；相同 event_id 相同内容跳过，不同内容拒绝。
7. 逐个导入各年的最新年度快照。月度和年度快照有重叠，建议优先仅使用年度完整快照，尚未结束的年再使用月份快照与最新手动年度快照。
8. 最后一次快照上点击恢复备份配置。日汇总与年度汇总从原始事件重算，metadata 里的统计仅用于比对，不盲目写回。
9. “从现在重新开始备份中的活动”需要明确确认；它创建新 UUID 并从当前时刻开始，不把备份到现在的空缺自动当作连续活动。
10. 对比全部累计秒数、各科目和跨年日分摊，运行 diagnostics、backupYear，验证新数据库能再次生成有效备份。

备份恢复是实际可运行的 App 导入流程，不需要手工逐行粘贴 Sheets。大批量导入仍受 Apps Script 配额限制；进度按已确认批次显示，失败后可以重试。

## 手机待同步队列恢复

1. 在原手机设置点击“导出本地恢复副本”。它包含当前活动、操作 UUID、顺序、云端快照、缓存原始记录和冲突分支，不含 Google token。
2. 将文件保存到安全位置。这个个人数据文件不要上传公开 GitHub。
3. 新手机/新站点连接同一后端，确保当前活动与待同步队列都为空。
4. 设置 → 恢复本地队列副本 → 选择导出的 JSON → 恢复本地副本。
5. 登录同步。恢复保留原 UUID：已经到达云端的请求会返回原回执；确实没到达的继续提交。
6. 若云端在导出后被其他设备修改，会触发 revision 冲突，不覆盖服务器。

## 多设备冲突

首次冲突后按钮冻结，队列保留。在冲突框先导出本地副本，再选择采用云端状态。本机未同步分支存入 IndexedDB conflicts，之后再导出本地副本仍能得到它。

当前版本不自动合并两台设备相互重叠的活动：这会产生无法判断的真实时间矛盾。可在导出 JSON 的 conflicts 数组中检查已完成 events，确定实际发生的记录后用开放 JSONL 和 manifest 流程导入空库/对齐后的库；活跃区间需要人工决定结束时刻。不要同时把两台手机当成主记录设备。

## 原始表被手动修改之后

推荐使用 PWA 编辑、拆分、删除，其统计随事务更新。如果你直接修改了 Sheets：

1. 先 backupYear 保存现状，停止其他设备提交。
2. 检查 event_id、ISO 8601、timezone、schema_version、整数 duration_seconds 全部合法。不要移动原始行到错误开始年份；跨年调整应使用 App 自动迁移。
3. 在 Editor 建立 `function repair2026(){ rebuildYear(2026); }`，保存并运行。
4. 若记录跨入下一年，还要重建 2027。重建会读取目标年和必要的前两年，包含最多 366 天跨界记录。
5. 日汇总和年汇总使用持久化计划替换，重建重复运行不会加倍；版本会增加，让旧设备缓存触发刷新/冲突保护。
6. 手动改表不是完整受审计的写入机制，可能破坏 UUID 索引；不要手工更换 UUID、开始年份或 deleted。

## 升级与迁移

原始 v1 字段不可原地改含义。未来 v2 应新增转换函数，逐年读取 → 新年度文件 → 校验有效 UUID 集合、总秒数、每科目秒数 → 备份 → 更换 file_index 指向。保留旧文件与 manifest。

每年默认不超过 100,000 原始行；事件定位/操作回执分布在按 UUID 前两个字符划分的 256 个索引文件。极端年度变化创建大量新科目，JSON 汇总单元格接近 45,000 字符会安全拒绝提交并保留队列，此时需迁移汇总为独立科目长表。限制是避免已知容量错误把事务卡死，不是自动支持无限数据。

## 常见故障

| 现象 | 处理 |
| --- | --- |
| Google 登录无法加载 | 手机网络验证 Google 可达；联网后重新打开设置 |
| AUTH_REQUIRED | 重新登录，token 过期/账号不对；不要清队列 |
| 来源无效 | ALLOWED_ORIGIN 必须与实际网页 origin 精确一致，去掉项目路径和尾斜线 |
| 请求一直超时 | 核对 /exec、Anyone、以 Me 执行、最新部署版本；检查 Apps Script Executions 是否到达 doPost；验证 iframe 回执是否被浏览器策略拦截 |
| 配额或执行超时 | 停止反复提交，等配额恢复；操作 UUID 和 pending 计划不清除，下一次恢复 |
| 恢复计划校验失败 | 保留 pending 指针与 Drive 文件，核对被手动修改/删除的临时文件；先导出并排查，不能直接清 pending |
| 后端日志出现公开端点异常流量 | 公开端点可能被恶意请求消耗平台配额；有效数据请求仍需签名与账号验证。必要时停用部署并迁移到有访问网关的方案 |
| 浏览器被 OPPO 系统关闭 | 重开恢复时间戳，联网登录补传；不能保证后台自动同步 |
| 手机空间不足/IndexedDB 无法写入 | 界面不会假装保存成功；先同步/导出已有数据，清其他空间，保留本站数据 |
| 名称修改后累计看起来不一致 | 科目按稳定 event_key 累计；分类按当时记录 category 判断。历史改分类需编辑历史记录 |
| 误删记录 | 删除保留墓碑；可以从删除前的有效备份恢复到新库，核对后迁移，或经人工检查恢复墓碑并重建 |

## ChatGPT 分析

Drive 的 sheets 是标准二维表：events 为原始记录，daily_summary 为日秒数表，Master/annual_summary 为年秒数表。自定义科目在 by_event_json 中，各分类在 by_category_json 中。常用科目还有固定秒数列。

可以请求：“读取 TimeTracker/Raw 的 2026、2027 年 daily_summary，按 date 分析最近 30 天；有效学习以 study_seconds 为准，时长转换成小时仅用于显示。”若要分析时间段、健身相关性或娱乐起点，则读取相关年度 events，按 timezone 切分自然日。不同年份事件跨界时保持 event_id 去重。具体连接器能读取哪些文件，以连接权限为准。
